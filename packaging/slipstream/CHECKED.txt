  What failed, and what it may mean: with "Lower delay" OFF the software renderer no longer
  keeps up. It showed 0.41 generated frames per real frame where the test asks for at least
  0.9, so frame pairs were skipped, the multiplier fell below 3X and in several runs "Lower
  delay" could not start at all; most of the other failed checks follow from that. The same
  test alone on another machine (e2e-quick number 44): 469 passed, 18 failed, 0.68 generated
  frames per real frame. Before one correction made on 27 November (a scan of HUD Guard that
  ran for every pixel in the middle of the picture) it was 438 passed, 25 failed, 0.42.
  WE DO NOT KNOW THE CAUSE FOR CERTAIN. The likely one is HUD Guard: it adds work to every real
  frame, and a software renderer does that work on the processor. A run of the same test with
  HUD Guard switched off was started (branch ck/e2e-rel17-gate-nohud, e2e-quick number 45) and
  had not finished when this was written. On a graphics card the same work is estimated at
  well under a millisecond, but THAT IS AN ESTIMATE: if frames are skipped or the delay rises
  on your PC with Live HUD Lock on, use the undo line of part A and send the log.
  HUD Guard's own end-to-end test (the real engine with the graphics debug layer, software
  renderer): 70 checks passed, none failed, in e2e-quick numbers 43 and 44.
