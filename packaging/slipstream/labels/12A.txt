THE SHORTEST WAY                                   the kit prints each session's time and its own >>> steps
  Package 12A is Package 12's program (the same experimental build 66) with a new test of what frame
  generation adds to the delay, part by part. If Package 12 is installed, install again anyway: it
  is quick and puts this kit's files in place.
  1. Double-click  Install-Slipstream.cmd          10 to 20 minutes (answer the NVIDIA neural runtime
                                                   question as you like; this test does not need it)
  2. Frame generation delay, part by part. Set Windows to 120 Hz (G-SYNC / variable refresh as you
     normally use it), open a Command Prompt in this folder and run this ONE line:
       Run-First-Test.cmd -Session smoothness -Pass 120 -Arms flt-off,flt-fg2,flt-fg2-phase,flt-fg2-hold,flt-fg2-grace,flt-fg2-headroom,flt-fg2-ull,flt-fg2-ull-prio,flt-fg2-ull-low
                                                   about 25 minutes, all automatic. Keep the same
                                                   steady camera motion in the same place in every
                                                   run. It compares: frame generation off, 2X as
                                                   installed, each low-latency part alone, all
                                                   parts, all parts with a high-priority present
                                                   queue, and all parts with VFG Low.
  3. Your own comparison in normal play (the only test of how it FEELS): in the experimental copy's
     folder (%LOCALAPPDATA%\Programs\PushFPS-slipstream-exp) make a text file slipstream.ini with
     the one line
       VEYRA_EXP_RP_FG_ULL = 1
     Restart that PushFPS, play 10 minutes with frame generation at 120 FPS; then delete the line,
     restart, play the same scene again. Note for each: responsiveness (mouse / stick), smoothness,
     stutter. Then double-click Collect-Diagnostics.cmd (one zip).
  4. Tell us your upscaling settings: is SR (upscaling) on, which method, and which target
     (1440p, 4K, ...). Frame generation works at the upscaled size, so 4K on a 1440p screen
     costs more GPU time on every frame.
  5. Only if you want the 180 FPS answer too: Windows at 180 Hz, then
       Run-First-Test.cmd -Session smoothness -Pass 180     about 36 minutes (3X at 180 against
                                                   the low-latency mode, which keeps 120 under VRR)
  Steps 2, 3 and 5 each end with ONE zip to send back. Nothing in this package has run on your PC.
  Still open from Packages 10 to 12, when you have time: -Session retest (about 25 min),
  -Session input (about 29 min), the "DLSS 5" four-way (-Session smoothness -Pass 120 -Arms
  nrp-base,nrp-nr,nrp-fg,nrp-nr-fg,nrp-nr-fg-adapt, about 14 min) and, with a capture card,
  -Session capture -Pass 120. And the name of your capture card.

WHAT IS NEW IN PACKAGE 12A   (test kit only; the program is exactly Package 12's)
  - The test of step 2 (docs\HARDWARE_TEST_PROCEDURE.md, "Frame generation latency, part by
    part"). Read per run: the age of real frames when shown (P50 / P95 / P99), the estimate of what
    frame generation adds, late presents, generated frames dropped, real and generated frames per
    second and how evenly frames were shown. These are software times inside the PC, not the delay
    from your hand to the screen; a part is only worth keeping if it lowers the age with the same
    evenness.
  - What to expect, by arithmetic only (docs\FG_LATENCY.md; nothing measured): at 60 -> 120 any
    interpolation waits for the next real frame, about 8 ms plus the first generated frame's GPU
    time; Package 12 as installed holds a real frame about 4 ms longer than that, and the
    low-latency mode removes that part. Lower than the wait itself needs frame generation off.
  - The kit now keeps the [present-priority] log line, and clears a VEYRA_TEST_PRESENT_ switch
    left in the Command Prompt so it cannot leak into every run.
NEW IN PACKAGE 12 (also in this package)
  - Where frame generation's delay comes from: docs\FG_LATENCY.md. The three largest parts: the
    wait for the next real frame (inherent to any interpolation); a real frame held for the whole
    frame generation delay even when no generated frame is shown (avoidable); and Remote Play's
    fixed delay instead of a measured one (avoidable, about 4 ms at 60 -> 120 by arithmetic).
  - Low-latency frame generation, switch VEYRA_EXP_RP_FG_ULL = 1 (or only some parts: hold, phase,
    headroom, grace). It removes the two avoidable parts. It can only show frames earlier, never
    later; it may drop a few more generated frames, and the picture jumps forward once when a hold
    starts and stands still once when it ends. There is no menu entry yet: nothing is measured.
  - Predicting frames instead of waiting for the next one (extrapolation) was studied and not
    built: NVIDIA's frame generation only interpolates, and it could not beat frame generation off
    for responsiveness.
  - The "DLSS 5" stutter: docs\NR_STUTTER.md. The option is NVIDIA's own neural runtime run on the
    decoded video, not NVIDIA's DLSS 5 built into games. Most likely cause (from the code, the size
    is an estimate): when a frame's work takes longer than one frame of the game, decoded frames are
    replaced before they are used and late frames lose their generated frames. By estimate, 2X at
    1440p fits; 3X or 180, upscaling to 4K, the highest frame generation quality, or the neural
    layer at 1440 or native size do not.
  - Switch VEYRA_EXP_RP_NR_ADAPT = 1: when time runs short, the neural layer reuses its last result
    on the next frames instead of running again. No buffer and no wait; its own motion pass adds a
    little GPU time to each real frame. Judge the picture by eye: a reused result is one frame old.
  - To try a switch in normal play: put its line in a file named slipstream.ini next to the
    experimental copy's PushFPS.exe (%LOCALAPPDATA%\Programs\PushFPS-slipstream-exp), one switch
    per line, then restart it. Delete the line to switch it off. The test kit ignores this file.
NEW IN PACKAGE 11 (also in this package)
  - Capture card frame generation: docs\CAPTURE_FG.md says what to expect (60 -> 120 at 2X should
    fit; 30 -> 120 needs 4X; 180 is a stretch; frame generation always waits for the next real
    frame: at least about 25 ms at 4X for a 30 FPS game, plus processing). NVIDIA's in-game DLSS
    frame generation cannot work on a captured picture; the session's DLSS-path arms feed NVIDIA's
    frame generation with motion estimated from the pictures. The capture session measures real
    and generated frames apart; repeated frames are never counted as new ones.
  - GTA V-style keys (button "Apply GTA V-style keys"): WASD, mouse camera, left click fire, right
    click aim, Shift run, Space jump, F vehicle, R melee, Q cover, Ctrl crouch, Tab weapon wheel,
    mouse wheel quick-swaps the weapon while aiming, E interact, Esc pause; on foot, aiming,
    vehicle and menu keys. GTA VI's reload button is not published: if it is another button in the
    game, put R on it. Every key can be changed. The button also sets the lowest-latency mouse
    handling (no smoothing window, no carry, report timing, 8-bit stick steps) and keeps your own
    sensitivities. This is a controller emulated from mouse and keyboard, not native mouse
    support: the PS5 only ever sees a controller.
  - Camera feel (switches, measured by the input session): mouse speed from the mouse's own report
    times, a stop that never keeps the stick moving after your hand stops, whole 8-bit stick
    steps. Your existing profiles send exactly what they sent before (tested on 1.6 million
    events).
  - Mouse and keyboard beside a capture card: add the line VEYRA_EXP_RP_KBM_CONTROL = 1 to a file
    named slipstream.ini next to the experimental copy's PushFPS.exe
    (%LOCALAPPDATA%\Programs\PushFPS-slipstream-exp), then in the capture card dialog switch the
    PS5 controller control on. The picture comes from the card; only the buttons go over Remote
    Play. Veyra users reported the controller control working on real consoles; whether the PS5
    keeps its HDMI picture (resolution, HDR) meanwhile is not known: check it on your card.
  - Guides: docs\KEYBOARD_MOUSE.md (last sections), docs\KBM_AUDIT.md.
ON WITHOUT A CHOICE  (experimental build only; Package 7 and your own PushFPS unchanged)
  - Nothing new in Packages 11 and 12. Still on, from Package 10 and earlier:
  - Fixes taken from Veyra: the controller queue drops inputs that are too old, the neural layer's
    clean shutdown, and the loader fix for its DLL.
  - chiaki-ng fixes: reorder-queue drop, send-buffer teardown, HTTP header bounds, PIN log line.
  - The FPS readout says "N FPS shown" or "N FPS submitted" (and "uneven" when it is); "shown" is
    worked out from the present times, not read from the screen.
  - The variable-refresh state is read again 5 s and 15 s after the picture starts. If G-SYNC
    engages only then, variable-refresh presentation starts mid-session (before, at the next
    display change).
  - Neural runtime: at an update, an unchosen packaged copy is removed (see section 1). When the
    file is present, its signature and SHA-256 are checked at start (about 1 s, an estimate); the
    NVIDIA runtime choice is offered only for a verified original, and a neural layer you never
    changed moves to the verified original once one is installed. New log lines [nr-runtime-status]
    and [nr-runtime-check].
  - Package 10, three fixes that can only remove delay or wasted work (each has a test switch to
    compare with the old behaviour; tested on Linux and GitHub only):
    * Sound now follows each picture's real arrival. In Package 9 it waited for an estimated
      video clock that falls behind when the PS5 sends fewer than 60 frames a second, up to 1.5 s.
    * A queued frame that arrived after the app's clock reading is no longer thrown away as
      stale (the rule Veyra and PushFPS themselves use).
    * Under a frame cap, frame generation no longer makes frames the cap throws away (e.g. 2X
      instead of 3X under a 120 FPS cap with a 59.94 FPS stream). It only ever lowers the
      multiplier; with variable refresh confirmed the counter can read below the cap (115, not 120).
  - Always logged: the PS5's real frame rate ([remoteplay-clock] wireFps=, about every 10 s), the

----- the install question (section 1) -----
   THE ONE QUESTION: the neural layer needs NVIDIA's own runtime file. The installer keeps it only
   when you say yes, and only when the file is an NVIDIA-signed original; it never installs a
   modified file. Without it everything else works, and the neural arms of the kit say
   "not installed: skipped". To answer in advance:
       Install-Slipstream.cmd -NeuralRuntime Yes       (or No; Ask is the default)
   UPDATING an earlier experimental copy (Package 7, 8A or 8B): an NVIDIA runtime copy that came with
   an earlier package without your yes is removed at this update, and a layer saved on it becomes
   unavailable. Answering no removes every copy, also one you added in Settings. Answer yes, or add
   it later in that copy's Settings, Components and licenses.
   THE OTHER THREE COPIES (original, stable, Package 7) use their older installers: on an NVIDIA PC
   they keep the NVIDIA-signed runtime file from Veyra's package without asking, as PushFPS 3.2.1
   does. Their neural layer still stays off until you turn it on.
