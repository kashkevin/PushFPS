THE SHORTEST WAY
  1. Double-click  Install-Slipstream.cmd          10 to 20 minutes. Then play as you do now:
                                                   capture card, 4K, 30 FPS game, 90 FPS.
  2. For the lower delay: start PushFPS from the experimental copy as with Package 14 (folder
     %LOCALAPPDATA%\Programs\PushFPS-slipstream-exp), play from the capture card, and in
     quick setup switch  "Lower delay (one predicted frame per real frame)"  on. The row shows
     only while the capture card picture plays with NVIDIA VFG at 3X; if something is missing
     it says what. One click, it applies at once (the picture may pause for a moment) and is
     remembered for the next start. The same click switches it off.
  Nothing to edit, no test to run: section 2 and later of this file (the measuring kit) are
  optional. Step 1 alone gives you parts B, C and D below.
  NOTHING IN THIS PACKAGE HAS RUN ON YOUR PC OR ON ANY REAL GRAPHICS CARD. Nothing is called
  fixed. If you ever want to tell us how it went with numbers, play a few minutes and
  double-click Collect-Diagnostics.cmd (one zip).

WHAT PACKAGE 15 CHANGES   (capture card, 4K, 30 FPS shown as 90 FPS; picture size untouched)
  Each line says how far it is proven: SIMULATED = our scheduling code run with made-up 4K-like
  timings; TESTED = unit tests / the Windows build machine's software renderer; nothing is
  HARDWARE-VERIFIED yet.
  A. "Lower delay" mode   (OFF until you switch it on; only NVIDIA VFG at 3X on a capture card)
     - Today each real frame waits until BOTH generated frames before it have been shown: by
       the schedule's arithmetic that is 22 ms of your 31 ms (part D shows your own split). With
       the mode on, the real frame is shown one displayed frame earlier: one generated frame,
       then the real frame, then one frame PREDICTED from the motion so far. The wait drops
       from 22 to 11 ms. 90 FPS and the 4K size stay.
     - What to expect on the readout: 11 ms less by the schedule's arithmetic, about 9 ms less
       in the simulation, so roughly 20 to 22 ms where you read 31 ms now, when the GPU has
       room. That is an expectation, not a measurement and not a promise. SIMULATED over 16
       kinds of GPU load (the simulator's own figures run higher than your readout; only the
       difference counts): average 37.6 -> 28.3 ms, a narrower spread, and more frames on the
       90 FPS grid (99.1 against 91.1 %), because a pair needs one NVIDIA generation run, not
       two. It is NOT the 15 ms you asked for: see "What 15 ms needs" below.
     - The price, honestly: one shown frame in three is a prediction, not a frame generated
       between two real ones. Where the app does not trust the motion it keeps the real
       picture in that part of the frame. You may see: a slight judder in fast camera turns,
       smoke, rain, explosions, flashes and fades; front edges of moving objects and thin lines
       (wires, railings) bending or jittering slightly; that frame a little softer where it
       moved. How visible this is, nobody knows yet: no simulation shows the picture.
     - It protects itself: it leaves the mode by itself when most predictions are unusable (45
       of the last 60, about 2 seconds) or when more than 2 of the last 60 predicted frames come
       too late, and tries again after 10 to 60 seconds. A third exit (three seconds in a row
       below 98 % on the 90 FPS grid) acts only after normal frame generation was measured at
       98 % or better for a whole second in the same session; with the row already on at start
       it usually has not been, so that exit does not act. A predicted frame in which more than
       half of the moving parts cannot be trusted is replaced by the real picture as a whole.
       It pauses during the app's own tests and comparison clips. It does not run with Live HUD
       Lock, exclusion boxes or Smoothness Mode, or whenever the multiplier in use is not 3X
       (adaptive multiplier or an output cap); the row says why. When the GPU is very busy some
       frames can have MORE delay than with the mode off (SIMULATED: where the old method would
       have skipped the pair; about 9 % of pairs near the GPU's limit, about half far over it).
     - The biggest unknown: the mode asks NVIDIA's frame generation for the second in-between
       frame without the first. That request has never run on a graphics card. If yours
       refuses it, the row says so, the mode stops for that run (the switch still shows on;
       off and on tries once more) and frame generation goes on as before. Only that decision
       and the row's text are TESTED; the refusal itself has never run (it needs a real card).
     - With the row off, every frame takes Package 14's path (an independent review of every
       changed line; the simulator agrees, but it runs this package's code, not Package 14's).
  B. The delay badge no longer blocks the fast display path   (ON)
     - The badge and the statistics overlay used to be cut out of the video window, which makes
       the window's shape complex. In your earlier Remote Play logs (120 FPS), frames reached
       the screen a median 7 to 9 ms after PushFPS handed them over while the shape was complex,
       with variable refresh reported off, and about 1 ms when it was one rectangle. That is a
       pattern in logs, not proof. Hovering the badge (part D) cuts its tip out again meanwhile.
     - Now they are drawn inside the picture itself, so while nothing else is over the picture
       the window stays one rectangle. By reading the code they are not in recordings, clips or
       streams (no test checks that yet). The readout number does NOT show this change: it
       stops where the frame is handed to Windows. Whether it helps on your screen, and whether
       G-SYNC then engages, is not known until your PC shows it.
  C. NVIDIA low latency can no longer keep holding back captured frames   (ON)
     - With "NVIDIA low latency" on, the app asks the driver to pause before each frame is read.
       On a capture card the console sets the pace, so a pause that runs past a frame's arrival
       can only add delay to that frame. The app now measures that, and if it keeps happening
       (not for a hiccup at start-up) it switches NVIDIA low latency off for that playback. The
       app's own settings (short queue, one frame waiting at most, sync, G-SYNC) stay.
  D. The readout says what it is made of   (ON, display and log only)
     - Hover the delay badge: picture processing + first generated frame + waiting for the
       frames shown before it + margin. The waiting part is calculated from the schedule.
       The number never includes the game, the console, the capture card or the display.
     - The log now always carries how the picture reaches the screen ([present-path]) and,
       every 10 seconds, delay average / median / P95 / P99, frame pacing, dropped and repeated
       frames and GPU time per stage ([fg-health]).
  E. In the box but switched off: finishing a frame's last copy early and handing it to Windows
     exactly on time (steadier timing, estimate). It cannot be proven never to delay the next
     frame's work, so it stays off (developers' switch VEYRA_EXP_RP_PRESENT_BLIT_AHEAD).

WHAT TO EXPECT, HONESTLY
  - Step 1 only: the readout stays about 31 ms. Part B acts after the point where the readout
    stops; part C lowers it only if the driver's pause really ran past the frames' arrival.
  - With "Lower delay" on: roughly 20 to 22 ms if the request works on your card and the GPU
    has room (expected, not measured).
  - Your 99 % steadiness target: SIMULATED, with the mode on it is missed in 5, 6 or 7 of the
    16 kinds of GPU load when a predicted frame costs 3, 6 or 10 ms (Package 14: 8 of 16); the
    average over all 16 is 99.1 % (Package 14: 91.1 %). Your real figure is in the log.
  - WHAT 15 MS NEEDS. Three research reports (NVIDIA Streamline / Reflex / Optical Flow, AMD
    frame generation and Windows presentation, frame generation models) agree: every method
    that generates frames BETWEEN two real ones holds the newest real frame back; only
    prediction removes that wait. With one predicted frame the delay is the real frame's own
    work + the first generated frame + 11 ms + margins; NVIDIA's generation costs about 6 to 7
    ms at 4K by an upstream developer's figure (not measured on your PC): about 20 ms.
    Mid-teens needs a much cheaper first generated frame: motion worked out once per pair at
    a smaller size, then both extra frames built from it at full 4K (our estimate 14 to 20 ms;
    whether it looks as good as NVIDIA's model is unproven). That is the next experimental
    branch. Two predicted frames would read a few ms, but the one published comparison found
    (a video-only model against interpolation) shows prediction from video alone clearly
    worse, so it will only ever be an option, never the default.
  - Not usable for captured video (checked against the documentation): NVIDIA's DLSS frame
    generation through Streamline, Reflex 2 Frame Warp, AMD's and Intel's frame generation
    (these need the game's own depth and motion data), NVIDIA's frame interpolation library
    (interpolation only, no D3D12 path).

NEW IN PACKAGE 12 (also in this package)
  - Where frame generation's delay comes from: docs\FG_LATENCY.md. The three largest parts: the
    wait for the next real frame (inherent to any interpolation); a real frame held for the whole
    frame generation delay even when no generated frame is shown (avoidable); and Remote Play's
    fixed delay instead of a measured one (avoidable, about 4 ms at 60 -> 120 by arithmetic).
  - Low-latency frame generation, switch VEYRA_EXP_RP_FG_ULL = 1 (or only some parts: hold, phase,
    headroom, grace). It removes the two avoidable parts. It can only show frames earlier, never
    later; it may drop a few more generated frames, and the picture jumps forward once when a hold
    starts and stands still once when it ends. There is no menu entry yet: nothing is measured.
  - Predicting frames instead of waiting for the next one (extrapolation) was studied and not
    built: NVIDIA's frame generation only interpolates, and it could not beat frame generation off
    for responsiveness.
  - The "DLSS 5" stutter: docs\NR_STUTTER.md. The option is NVIDIA's own neural runtime run on the
    decoded video, not NVIDIA's DLSS 5 built into games. Most likely cause (from the code, the size
    is an estimate): when a frame's work takes longer than one frame of the game, decoded frames are
    replaced before they are used and late frames lose their generated frames. The four-way test of
    Package 12 measures it on your PC.
  - Switch VEYRA_EXP_RP_NR_ADAPT = 1: when time runs short, the neural layer reuses its last result
    on the next frames instead of running again. No buffer and no wait; its own motion pass adds a
    little GPU time to each real frame. Judge the picture by eye: a reused result is one frame old.
  - To try a switch in normal play: put its line in a file named slipstream.ini next to the
    experimental copy's PushFPS.exe (%LOCALAPPDATA%\Programs\PushFPS-slipstream-exp), one switch
    per line, then restart it. Delete the line to switch it off. The test kit ignores this file.

----- the install question (section 1) -----
   THE ONE QUESTION: the neural layer needs NVIDIA's own runtime file. The installer keeps it only
   when you say yes, and only when the file is an NVIDIA-signed original; it never installs a
   modified file. Without it everything else works, and the neural arms of the kit say
   "not installed: skipped". To answer in advance:
       Install-Slipstream.cmd -NeuralRuntime Yes       (or No; Ask is the default)
   UPDATING an earlier experimental copy (Package 7, 8A or 8B): an NVIDIA runtime copy that came with
   an earlier package without your yes is removed at this update, and a layer saved on it becomes
   unavailable. Answering no removes every copy, also one you added in Settings. Answer yes, or add
   it later in that copy's Settings, Components and licenses.
   THE OTHER THREE COPIES (original, stable, Package 7) use their older installers: on an NVIDIA PC
   they keep the NVIDIA-signed runtime file from Veyra's package without asking, as PushFPS 3.2.1
   does. Their neural layer still stays off until you turn it on.
