ON WITHOUT A CHOICE IN 10  (experimental build only; Package 7 and your own PushFPS unchanged)
  - Fixes taken from Veyra: the controller queue drops inputs that are too old, the neural layer's
    clean shutdown, and the loader fix for its DLL.
  - chiaki-ng fixes: reorder-queue drop, send-buffer teardown, HTTP header bounds, PIN log line.
  - The FPS readout says "N FPS shown" or "N FPS submitted" (and "uneven" when it is); "shown" is
    worked out from the present times, not read from the screen.
  - The variable-refresh state is read again 5 s and 15 s after the picture starts. If G-SYNC
    engages only then, variable-refresh presentation starts mid-session (before, at the next
    display change).
  - Neural runtime: at an update, an unchosen packaged copy is removed (see section 1). When the
    file is present, its signature and SHA-256 are checked at start (about 1 s, an estimate); the
    NVIDIA runtime choice is offered only for a verified original, and a neural layer you never
    changed moves to the verified original once one is installed. New log lines [nr-runtime-status]
    and [nr-runtime-check].
  - Package 10, three fixes that can only remove delay or wasted work (each has a test switch to
    compare with the old behaviour; tested on Linux and GitHub only):
    * Sound now follows each picture's real arrival. In Package 9 it waited for an estimated
      video clock that falls behind when the PS5 sends fewer than 60 frames a second, up to 1.5 s.
    * A queued frame that arrived after the app's clock reading is no longer thrown away as
      stale (the rule Veyra and PushFPS themselves use).
    * Under a frame cap, frame generation no longer makes frames the cap throws away (e.g. 2X
      instead of 3X under a 120 FPS cap with a 59.94 FPS stream). It only ever lowers the
      multiplier; with variable refresh confirmed the counter can read below the cap (115, not 120).
  - Always logged: the PS5's real frame rate ([remoteplay-clock] wireFps=, about every 10 s), the
    expiry rule and the causes of each keyframe wait ([remoteplay-ingress]), the audio rule in use
    ([remoteplay-audio] pictureTerm=), each cap-fit change ([push-cap-fit]) and the share of dated
    presents (scanoutKnownPct=).

----- the install question (section 1) -----
   THE ONE QUESTION: the neural layer needs NVIDIA's own runtime file. The installer keeps it only
   when you say yes, and only when the file is an NVIDIA-signed original; it never installs a
   modified file. Without it everything else works, and the neural arms of the kit say
   "not installed: skipped". To answer in advance:
       Install-Slipstream.cmd -NeuralRuntime Yes       (or No; Ask is the default)
   UPDATING an earlier experimental copy (Package 7, 8A or 8B): an NVIDIA runtime copy that came with
   an earlier package without your yes is removed at this update, and a layer saved on it becomes
   unavailable. Answering no removes every copy, also one you added in Settings. Answer yes, or add
   it later in that copy's Settings, Components and licenses.
   THE OTHER THREE COPIES (original, stable, Package 7) use their older installers: on an NVIDIA PC
   they keep the NVIDIA-signed runtime file from Veyra's package without asking, as PushFPS 3.2.1
   does. Their neural layer still stays off until you turn it on.
